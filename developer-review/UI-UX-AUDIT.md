# UI/UX Audit

**Read this scope statement before the findings below.** Mandate §6.4/§6.5 require
screen-by-screen, viewport-by-viewport, state-by-state verification, ideally backed by
actual browser screenshots or Playwright execution. **No browser was launched and no
screenshot was captured during this audit** (see `appendix/ENVIRONMENT-GAPS.md` EG-001,
EG-002). Every claim below is therefore explicitly labeled by verification state, and no
claim asserts a visual result that was not actually observed. This is a **static,
source-code-only** pass over the UI/UX dimension, which — honestly — only partially
satisfies the mandate's intent for this dimension. Treat this document as a scoping and
triage aid for a follow-up session that has runtime/browser access, not as a completed
UI/UX certification.

**One specific, non-deferred accessibility-adjacent observation:** The two
`dangerouslySetInnerHTML` call sites noted in §1 render rich-text/resume content that
is very plausibly user-authored (resumes, cover letters). Beyond the XSS concern already
flagged, unsanitized or poorly-structured injected HTML can also produce an inaccessible
DOM (missing semantic structure, broken heading hierarchy) for assistive technology users
reading a shared/public resume. This is flagged as a **combined
security+accessibility review priority** for the two cited files in a follow-up session,
not as a confirmed defect in this one (no content sample was rendered or inspected for
actual structural correctness).

## 7. Implementation recommendations (process, not code)

1. Prioritize running the **existing** `engine-responsive.spec.ts` and `test:candidate`
   Playwright suites in a real environment before writing any *new* UI/UX tests — the
   project already has infrastructure for this that this audit could not exercise.
2. Use the existing `docs/ai-settings/responsive-a11y-report.md` (inside the audited
   repo) as a template for producing equivalent reports for the other 10 screens listed
   in §2, since that report format and its underlying test (`engine-responsive.spec.ts`)
   already exist and are proven to work for one surface.
3. Resolve the `dangerouslySetInnerHTML` sanitization question (§1/§4) before any other
   UI/UX work, given its dual security+accessibility relevance.

The sections above were scoped to source inspection and explicitly marked
`RUNTIME VERIFICATION DEFERRED`. That deferral is now partially lifted: Chromium
149.0.7827.0 + axe-core 4.14.0 ran against the live application at 375×667 and

| A11Y-002 | `label-content-name-mismatch` (serious) | 2 | `pages/landing.tsx:79`, `:296` logo `<a aria-label="IME365 Home">` | visible text not contained in accessible name → voice-control failure |
