# 03 — Legacy Reference Inventory and Intent Classification

**Purpose of this section:** establish *what the business genuinely depends on*, decoupled from how legacy implemented it. Every capability below is classified once, and the classification is what §04 (coverage) and §10 (recommendations) are judged against.

**Classification key**

| Class | Meaning | Consequence in this review |
|---|---|---|
| **MUST** — Must exist in new system | Business-critical: losing it breaks an operational or security duty | Its absence is a gap requiring a required modification |
| **REDESIGN** — Should exist, redesigned | Needed, but the legacy implementation is deficient (fragile, over-privileged, misleading, or unusable) | Its absence is a gap; reinstating legacy shape verbatim is *not* an acceptable fix |
| **DEFECT** — Legacy defect | Legacy behaviour was wrong; the new system must do the correct thing | Never a benchmark; if the new system reproduced it, that reproduction is itself a defect |
| **OBSOLETE** — Obsolete | Genuinely no longer needed; why is documented | Not a gap if missing |
| *(out of scope)* | Not admin-plane | Not assessed |

**Evidence base.** Legacy surfaces were inventoried from three mutually confirming sources:

1. Tab routes: `src/components/admin/Admin.jsx:840-960` → **24 concrete tab routes**.
2. Settings screens: `src/components/admin/sidebar/sidebar.jsx:68-111` → **31 settings screens** across 6 groups, each with an explicit `permission:` or `superAdminOnly:` gate.
3. The APIs each screen calls, extracted per component (e.g. `src/components/admin/audit/AdminAuditLogs.jsx` calls `/api/admin/audit-logs` and `/api/admin/audit-logs/stats`; `src/components/admin/tenants/PlatformTenants.jsx` calls `/api/enterprise/platform/tenants`).

Where a capability's *business rule* is inferred rather than stated in code, the row says *(inferred)* and gives the basis. No row asserts a user requirement that is not visible in legacy code.
